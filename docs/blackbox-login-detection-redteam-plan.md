# 블랙박스 로그인 탐지 레드팀 테스트 기획서

- 문서 상태: 초안 (v0.1)
- 작성일: 2026-09-18
- 대상 시스템: `POST /v1/detect` (요청 예시 아래 참조)
- 전제: 이 문서를 작성하는 시점에는 대상 탐지 시스템(가칭 "탐지 서버")의 내부 로직/코드를 전혀 참조하지 않았다. 모든 내용은 업계에 공개된 일반적인 로그인 이상탐지(anomaly detection) 기법에 대한 지식만을 근거로 한다.

```
curl -s -X POST http://127.0.0.1:8080/v1/detect \
  -H "Content-Type: application/json" \
  -d '{
    "ip": "203.0.113.1",
    "account_id": "test_user@example.com",
    "login_result": "success"
  }'
```

---

## 1. 목적 및 배경

자체적으로 구축한 로그인 이상탐지 시스템("EdgeSentry" 계열)의 방어력을 검증하기 위해, **내부 로직을 전혀 모르는 외부 공격자 시점**에서 탐지를 회피할 수 있는 요청 패턴을 가설로 세우고, 이를 실제로 테스트하여 사각지대(false negative)를 찾아낸다.

- 목표는 "회피 성공"이 아니라 **"탐지 시스템이 어떤 유형의 회피 시도를 놓치는지 목록화"**하는 것이다.
- 발견된 사각지대는 방어 팀(탐지 시스템 개발자)에게 전달되어 탐지 규칙/모델을 보강하는 데 사용된다.
- 본 문서와 후속 테스트는 **본인 소유 또는 명시적으로 테스트 승인을 받은 스테이징 환경**에서만 수행한다. 프로덕션 계정, 실제 사용자 데이터, 제3자 시스템에는 절대 사용하지 않는다.

## 2. 범위 및 전제 조건

| 항목 | 내용 |
|---|---|
| 대상 | `/v1/detect` 단일 엔드포인트 (로그인 이벤트 사후 판정 API로 추정) |
| 접근 수준 | 블랙박스 — 응답 스키마·차단 여부만 관찰 가능, 내부 스코어링 로직 미지 |
| 공격자 전제 | 이미 유효한 자격증명(정상 계정 비밀번호 등)을 확보한 상태에서 "이 로그인이 의심스럽지 않다"고 판정받으려는 계정 탈취(ATO) 후속 단계 시나리오 |
| 실행 환경 | 로컬/스테이징 (`127.0.0.1:8080`), 프로덕션 트래픽 아님 |
| 제외 범위 | 자격증명 획득 자체(피싱, 크리덴셜 스터핑 등), 대상 시스템 인프라 침투 |

## 3. 위협 모델: 공격자가 통제할 수 있는 변수

요청 바디에 노출된 필드(`ip`, `account_id`, `login_result`)와 HTTP 계층에서 공격자가 실제로 조작 가능한 것들을 분리해서 정리한다.

### 3-1. 요청에 명시적으로 드러난 필드
- `ip`: 공격자가 어떤 IP에서 요청을 보내는지 (프록시/VPN/봇넷 경유로 조작 가능)
- `account_id`: 대상 계정
- `login_result`: 이 필드가 클라이언트가 자유롭게 채워 보내는 값인지, 서버가 실제 인증 결과를 바탕으로 기록하는 값인지에 따라 위협 성격이 완전히 달라짐 (§6 참고)

### 3-2. 요청 바디 밖에서 공격자가 통제 가능한 변수 (업계 일반 탐지 신호 기준)
- 요청 **빈도/시간 간격** (동일 IP·계정에 대한 시도 횟수, 시간대)
- **소스 IP의 평판/유형** (주거용 IP vs 데이터센터/호스팅 IP vs 알려진 프록시·Tor 노드)
- **지리적 일관성** (계정의 과거 로그인 위치 대비 impossible travel 여부)
- **기기/클라이언트 지문** (User-Agent, TLS 핸드셰이크 특성(JA3), HTTP 헤더 순서 등 — 이 API 스펙에는 없지만 실제 로그인 플로우 앞단에는 존재할 가능성)
- **행동 패턴** (다수 계정에 분산 시도하는지 vs 특정 계정 집중, 성공/실패 비율)
- **계정 자체의 과거 이력** (해당 `account_id`가 이전에 이 IP/기기와 연결된 적이 있는지)

## 4. 탐지 시스템이 일반적으로 참조할 것으로 가정하는 신호 (업계 표준 기준, 사각지대 탐색용 체크리스트)

| # | 신호 카테고리 | 설명 | 관련 필드 |
|---|---|---|---|
| S1 | IP 평판 | 데이터센터/호스팅/Tor/공개 프록시 여부, 과거 악성 이력 (AbuseIPDB류 DB) | `ip` |
| S2 | 지리 일관성 (Impossible Travel) | 직전 로그인 위치와의 거리/이동 가능 속도 | `ip` (역지오로케이션) |
| S3 | 빈도·속도 (Velocity) | 동일 IP의 계정 순회 시도 수, 동일 계정의 시도 간격 | `ip`, `account_id` |
| S4 | 계정-자산 연관성 | 이 IP가 해당 계정과 과거에 연결된 적 있는지 (device/IP 신뢰 이력) | `ip`, `account_id` |
| S5 | 시간대 패턴 | 계정의 평소 활동 시간대와의 괴리 | 요청 시각 |
| S6 | 성공/실패 비율 | 동일 IP에서 다수 계정에 실패가 반복되다 하나만 성공하는 패턴(스터핑 흔적) | `login_result`, `ip` |
| S7 | 분산도 | 하나의 캠페인이 소수 IP에 집중되는지, 넓게 분산되는지 | `ip` |

이 체크리스트는 "공격자가 무엇을 흉내 내야 정상처럼 보이는가"가 아니라, **"우리 탐지 시스템이 이 신호들 중 실제로 무엇을 보고, 무엇을 놓치는지 검증하기 위한 테스트 축"**으로 사용한다.

## 5. 테스트 시나리오 매트릭스 (가설 → 검증 방법)

각 시나리오는 "이런 조합이면 탐지될까, 통과될까?"를 확인하기 위한 것이며, 실제 실행은 §7의 승인 절차를 거친 스테이징 환경에서만 진행한다.

| 시나리오 | 가설 | 검증 방법 |
|---|---|---|
| T1: 단발성 정상 요청 | 기존 이력 있는 IP+계정 조합, 낮은 빈도 → 통과 (베이스라인) | 1회 요청, 응답 기록 |
| T2: 데이터센터 IP | 클라우드/호스팅 IP 대역에서 요청 시 차단되는지 | 알려진 클라우드 IP 대역으로 반복 요청 |
| T3: 고빈도 요청 | 동일 IP로 짧은 시간 내 다수 계정 요청 시 velocity 임계값 탐지 여부 | 초당 N회, 계정 M개 순회 |
| T4: 저속·분산 (Low & Slow) | 요청 간격을 늘리고 IP를 소수 로테이션하면 S3 임계값을 우회하는지 | 긴 간격 + IP 2~3개 순환 |
| T5: 지리적 불일치 | 계정 이력과 동떨어진 국가 IP로 단발 요청 시 반응 | 해외 IP로 1회 요청 |
| T6: `login_result` 조작 (§6) | 클라이언트 제공 값이 그대로 신뢰되는지 | success/failure 값 변경 후 응답 비교 |
| T7: 계정 순회 vs 계정 고정 | 동일 IP가 여러 `account_id`를 시도하는 경우와 하나만 반복하는 경우 판정 차이 | 계정 목록 로테이션 |

## 6. 별도 확인이 필요한 설계 이슈 (탐지팀에 즉시 공유 권장)

블랙박스 관점에서 요청 스펙만 봤을 때, 아래는 탐지 로직과 무관하게 **API 설계 자체의 신뢰 경계 문제**로 보인다. 이는 "회피 기법"이 아니라 "이 필드를 누가 채우는가"에 대한 근본 질문이다.

- `login_result`가 클라이언트(로그인 처리 서버가 아닌 임의의 호출자)가 자유롭게 채워 보낼 수 있는 값이라면, 공격자는 실패한 로그인 시도도 `"success"`로 보고해 탐지 시스템의 학습 데이터/통계 자체를 오염시킬 수 있다.
- 이 API가 인증 서버 내부망에서만 호출 가능한지(mTLS, 내부 네트워크 제한, 서비스 간 인증 토큰 등), 아니면 외부에서도 도달 가능한지 확인이 필요하다. 도달 가능하다면 이는 탐지 회피 이전에 **입력 신뢰성(트러스트 바운더리) 문제**로, 탐지 정확도 자체를 무력화할 수 있는 더 심각한 이슈다.
- 권장: 이 문서의 T6 시나리오를 최우선으로 검증하고, 필요 시 별도 이슈로 분리해 트러스트 바운더리 문서를 작성한다.

## 7. 실행 절차 및 가드레일

1. 본 테스트는 소유자 본인 승인 하에 `127.0.0.1` 로컬/스테이징 환경에서만 실행한다.
2. 사용하는 `account_id`는 테스트 전용 계정만 사용하며(`test_user@example.com` 등), 실제 사용자 계정을 사용하지 않는다.
3. 각 시나리오 실행 결과(요청 파라미터, 응답, 차단 여부)는 `results/` 디렉터리에 구조화된 형식(JSON/CSV)으로 기록한다.
4. 결과는 회피 성공 여부가 아니라 **"탐지 규칙이 커버하는 신호 vs 커버하지 않는 신호"** 관점으로 정리한다.
5. 발견된 모든 사각지대는 방어 시스템 이슈 트래커에 등록하고, 본 리포지토리에는 공격 성공 재현 스크립트를 그대로 방치하지 않는다 (별도 비공개 채널로 공유하거나 즉시 패치 후 아카이빙).

## 8. 측정 지표

- **탐지율**: 시나리오별 차단/플래그 처리 비율
- **회피 성공률**: 통과된 시나리오 수 / 전체 시나리오 수 (낮을수록 방어 우수)
- **커버리지 갭**: §4 신호 카테고리(S1~S7) 중 실제로 반응이 관찰된 것 vs 관찰되지 않은 것
- **오탐 가능성 참고**: 정상 사용자 시뮬레이션(T1)이 오탐되지 않는지도 함께 확인 (탐지 강화가 정상 트래픽을 해치지 않는지)

## 9. 후속 조치

- 본 문서는 테스트 결과가 나오는 대로 "발견된 사각지대" 섹션을 추가해 업데이트한다.
- 사각지대가 확인되면 탐지 시스템 담당자와 함께 규칙/모델 보강 우선순위를 정한다.
- 이후 자동화 스크립트가 필요하면(사용자 승인 시) 별도 기획을 거쳐 Python으로 모듈화된 테스트 러너를 구현한다 (요청 시나리오 생성 모듈, 실행 모듈, 결과 기록 모듈 분리).

---

**요약**: 이 문서는 공격 성공을 위한 실전 매뉴얼이 아니라, 자체 탐지 시스템의 블랙박스 사각지대를 찾기 위한 레드팀 테스트 설계서다. 모든 실행은 자체 소유 스테이징 환경, 테스트 전용 계정에 한정한다.
